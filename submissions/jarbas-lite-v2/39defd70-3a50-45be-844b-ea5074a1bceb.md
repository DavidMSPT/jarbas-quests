**Task Title:** Debugging Intermittent NullReferenceException in a Multi‑Threaded .NET Core 6.0 Service    **Description:**   I am maintaining a .NET Core 6.0 background service that processes messages from an Azure Service Bus queue. The service uses a `ConcurrentDictionary<string, Processor>` to cache per‑tenant processor instances. Each processor holds a reference to an `HttpClient` and a `DbContext` (EF Core).    Occasionally, under high load, the service throws a `System.NullReferenceException` at the line `processor.HttpClient.SendAsync(request)` inside the `ProcessMessageAsync` method. The exception stack trace points to the `processor` variable being null, but a `ConcurrentDictionary.TryGetValue` check immediately precedes the call and returns `true`. The issue appears to be race‑condition‑related, possibly due to the processor being removed from the dictionary by a cleanup task that runs every 5 minutes, which disposes the processor and removes the entry.    **What I need:**    1. A thorough analysis of the likely race condition causing the intermittent `NullReferenceException`.   2. Recommendations for thread‑safe patterns to manage the lifecycle of cached objects (e.g., using `GetOrAdd`, `Lazy<T>`, or `ImmutableDictionary`).   3. Code changes to prevent the processor from being disposed while it is in use, including any necessary synchronization primitives or redesign of the cleanup logic.   4. A brief explanation of how to instrument the code with diagnostics (e.g., `ILogger`, `EventSource`, or `dotnet-trace`) to capture the exact timing of the failure for future debugging.    **Constraints:**    - Must remain within the existing architecture (no full rewrite to a DI container).   - The solution should keep the service highly performant under load (target >10,000 messages/min).   - Use only libraries that are already part of the .NET 6 runtime or are publicly available on NuGet.    **Deliverables:**    - A detailed written analysis (≈150 word
